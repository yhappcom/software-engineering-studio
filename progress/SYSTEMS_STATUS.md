**NEW SYNTHESIS — enumeration-safe provider collision:** current Firebase enumeration protection disables/deprecates `fetchSignInMethodsForEmail()` as a provider-discovery mechanism; current JS reference states it returns an empty list under protection. Therefore LogMate collision recovery cannot depend on identifier-first provider lookup even though an older Firebase Flutter error-handling sample still shows that pattern. Signed-out collision returns a generic typed recovery state; the user explicitly authenticates a supported method, then the app re-observes UID and runs normal owner resolution. Authenticated UID A linking a credential already owned by UID B must fail closed without automatically signing into/merging B while A's ledger is open. Any pending credential is transient recovery material and may be linked only after target-account authentication with before/after same-UID assertion. Firebase's generic application-data merge example is not LogMate owner authority.

Remote-invalidation transfer: Firebase local session restoration and current local ledger ownership must be separated from fresh server acceptance. Admin-side disable/delete does not itself trigger Flutter Auth streams; network failure is not revocation and positive rejection is not generic sign-out. Cloud/Sync authority must stop on positively observed rejection. The policy for admin-side disable/delete remains distinct from voluntary account deletion.

Deletion-saga transfer: account deletion is a multi-system, partially irreversible saga rather than `currentUser.delete()`. Firebase requires recent authentication for deletion. For Apple-linked accounts, Firebase/Apple guidance requires fresh Apple authorization and token revocation. The saga preserves same-UID reauthentication, provider-specific revocation, product-data erasure, Firebase identity deletion, local-data erasure, crash/restart resume, and idempotent retry as distinct states. Firebase identity absence is not proof that product or local data was erased. Google Play additionally requires an external web deletion-request resource.

**PROJECT DECISION — voluntary deletion:** once the user confirms account deletion, normal local access is permanently revoked. The deletion saga must delete both server-side user data and device-local LogMate data. A durable deletion-pending/locked state prevents Home/logbook re-entry while partial deletion is retried after crash/network failure. No retained local archive path is part of the normal deleted-account state.

**PROJECT DECISION / SYNTHESIS — recent access visibility:** persisted sessions mean a returning completed user may enter Home without a new sign-in.
