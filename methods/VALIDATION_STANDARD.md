# Engineering Validation Standard

## Principle

Engineering knowledge is not production-grade because it is plausible, documented, popular, or demonstrated once. Evidence must match the claim.

A green executable result is not self-interpreting. The Studio must preserve what claim was tested, where the expected behavior came from, what oracle produced the verdict, and what the evidence cannot establish.

## Evidence ladder

Use the strongest feasible rung:

1. `SOURCE` — specification, official docs, standards, primary implementation docs.
2. `MODEL` — first-principles explanation with explicit assumptions.
3. `WORKED EXAMPLE` — bounded example showing expected mechanism.
4. `EXECUTABLE TEST` — reproducible code/test with recorded environment.
5. `FAILURE CASE` — representative breakage, invalid input, race, interruption, process death, partial failure, or boundary condition.
6. `DEBUG/ROOT CAUSE` — evidence connecting symptom to mechanism.
7. `ALTERNATIVE` — materially different implementation or architecture comparison.
8. `TRANSFER VALIDATION` — same conclusion tested in another platform/product/context.
9. `PRODUCTION EVIDENCE` — observed real-project/runtime evidence with exact ref/version/release context.

## Test Evidence Contract

For substantial executable evidence, preserve this chain when materially applicable:

`CLAIM → SPEC/PROPERTY → TARGET → INPUT/STATE → ORACLE → ENVIRONMENT → OBSERVATION → VERDICT → FAILURE MODEL → REPRODUCTION DATA → EVIDENCE LIMIT`.

Definitions:

- **CLAIM** — the exact engineering statement the evidence is intended to support;
- **SPEC/PROPERTY** — the requirement, invariant, model, standard or other rule that defines expected behavior;
- **TARGET** — the exact system/unit/component/build being exercised;
- **INPUT/STATE** — the selected input plus relevant precondition/state;
- **ORACLE** — the human or mechanical decision mechanism that judges the observed outcome;
- **ENVIRONMENT** — toolchain, runtime, OS/platform/device/build/configuration and dependencies that can affect behavior;
- **OBSERVATION** — what actually happened;
- **VERDICT** — pass/fail/inconclusive under the oracle;
- **FAILURE MODEL** — which defect/failure classes the test is intended to expose and which are outside scope;
- **REPRODUCTION DATA** — exact inputs/fixtures/seeds/config/ref/logs needed to repeat the evidence;
- **EVIDENCE LIMIT** — conclusions that must not be inferred from the result.

A missing or invalid oracle can make a fully automated test weak evidence. An assertion is only the mechanical verdict mechanism; it does not prove that the expected value or property is correct.

## Validation record

When executable validation is material, record:

- question/hypothesis and exact claim;
- specification/property source;
- oracle and its independence/limitations;
- environment/toolchain/versions;
- exact code or fixture location/ref;
- setup, prestate and inputs;
- random seed or deterministic generation details when applicable;
- expected result;
- observed result;
- verdict;
- failure variants/failure model;
- interpretation/root-cause status;
- limitations/evidence boundary;
- reproducibility notes, including relevant external dependency/configuration identity.

For product audits/tests, additionally record:

`repository → exact ref/tag/branch/commit → declared version if available → evidence date`.

## Oracle discipline

Before treating a passing test as correctness evidence, ask:

1. What exact claim does this test support?
2. Where does the expected behavior come from?
3. Can the oracle disagree with the implementation if the implementation is wrong?
4. Is the expected result generated by duplicated production logic or another shared defect source?
5. Which states, inputs and failures are absent?
6. What environment/build/runtime assumptions matter?
7. Can another execution reconstruct the relevant conditions?
8. Does the evidence show a failure only, or also establish root cause?
9. What conclusion would be invalid to infer from this pass?

Prefer oracle independence proportional to risk: explicit authoritative examples, independently derived calculations, invariants, reference models/implementations, cross-implementation comparison, standards/domain tables, or qualified human/domain judgment when automation cannot decide.

## Reproducibility discipline

Replication is stronger than “I can run it again on my machine.” Preserve enough context for another execution to reconstruct the relevant conditions.

Where applicable record:

- exact code/ref;
- runtime/compiler/framework/SDK version;
- OS/platform/device/build mode;
- input/fixture/schema/prestate;
- configuration and feature flags;
- seed and generated-input method;
- locale/timezone/clock assumptions;
- network/cache/storage/external-service state;
- dependency versions/endpoints/mocks;
- failure signature/output/logs;
- cleanup/recovery procedure.

A fixed random seed controls only the randomness represented by that seed. It does not prove determinism of threads, clocks, networks, storage, scheduling, external systems or the target program generally.

## Common invalid shortcuts

Do not equate:

- test pass with global correctness;
- code coverage with correctness;
- assertion presence with a valid oracle;
- deterministic input generation with globally deterministic software;
- reproducible failure with proven root cause;
- one benchmark run with performance truth;
- one platform with cross-platform behavior;
- simulator/emulator with physical-device evidence when the distinction matters;
- successful write with durability;
- no observed crash with reliability;
- retry with idempotency;
- encryption presence with secure system design;
- default branch with production;
- type safety with runtime correctness;
- unit tests with system integration correctness;
- a framework abstraction with an OS/platform guarantee.

## Failure-first expectation

For topics involving persistence, sync, concurrency, migrations, security, release, or recovery, validation should deliberately include failure paths before PASS.

Examples:
- process killed between operations;
- network drop/timeout/reorder;
- duplicate request/event;
- stale or conflicting state;
- storage full/corrupt/invalid input;
- schema mismatch/migration interruption;
- permission revoked;
- dependency/build/release failure;
- clock/timezone/version mismatch when relevant.

A failure observation is not automatically a root-cause proof. Preserve the progression:

`failure observation → reproduction → isolation → causal hypothesis → check/falsification → root cause → fix → regression evidence`.

## Gate discipline

A specialist status must state why evidence is sufficient for PASS and what remains OPEN. Missing human, device, production, security-review, domain-oracle, cross-platform, or field evidence must remain explicit rather than simulated.
