# Q005 — Debugging, Fault Isolation & Observability Foundations

Status: **IN STUDY — first integrated Foundation block complete**  
Evidence date: 2026-09-17

## Problem / scope

A visible failure is not a root cause. Debugging needs a disciplined transition from symptom to reproducible evidence, isolation, causal hypothesis, falsification/intervention, root cause, fix, and regression evidence. Observability helps expose internal execution state, but telemetry volume or a correlated trace is not itself causal proof.

This block tests a narrow but reusable claim: **the same external symptom can be generated by different internal defects; boundary observations tied to an independent property can discriminate candidates that final-output logging cannot.**

## SOURCE

OpenTelemetry defines traces, metrics and logs as different signals and documents context propagation as the mechanism that allows signals across execution/service boundaries to be correlated. Its Logs specification describes TraceId/SpanId and resource context as mechanisms for correlating log records with traces and their origin.

These sources establish correlation mechanics, not root-cause inference. A trace/log link shows that observations belong to related execution context; it does not prove which observed event caused a failure.

## SYNTHESIS — debugging evidence chain

Use the following chain when the failure warrants root-cause claims:

`symptom → reproduction → scope/isolation → causal hypothesis → discriminating observation or intervention → falsification/confirmation → root cause → fix → regression evidence`

Important separations:
- `symptom != root cause`;
- `correlation != causation`;
- `log line != invariant`;
- `exception location != necessarily defect origin`;
- `reproducible failure != proven cause`;
- `fix made symptom disappear != automatically unique root cause` unless competing explanations were adequately excluded.

### Test Evidence Contract

- **CLAIM:** final-output-only evidence can be observationally ambiguous; stage-boundary evidence judged against an independent property can isolate which stage first violated the contract.
- **SPEC/PROPERTY:** for input `x`, the normalize boundary must satisfy `normalized == decoded * 2`; final output for input `5` must equal `10`.
- **TARGET:** deterministic three-stage Python model (`decode → normalize → aggregate`).
- **INPUT/STATE:** raw value `5`; two independent injected defects, one in normalize and one in aggregate.
- **ORACLE:** independent boundary property plus final expected result.

- **OBSERVATION:** both independent defects produced the identical external result `11`. With correlated stage observations, normalize-defect trace was `decoded=5, normalized=11, output=11`; aggregate-defect trace was `decoded=5, normalized=10, output=11`.
- **VERDICT:** PASS for the bounded claim. Final symptom alone did not discriminate the two causes; the normalize boundary property did.
- **FAILURE MODEL:** two deterministic single-process computation-stage defects with the same final symptom.
- **REPRODUCTION DATA:** fixture above; no randomness.
- **EVIDENCE LIMIT:** no claim about production telemetry systems, distributed clock ordering, sampling, dropped logs, crash dumps, Flutter DevTools, native symbolication, or automated causal inference.

### DEBUG / ROOT CAUSE

The first contract violation differs despite identical final output:
- normalize-defect case first violates `normalized == decoded * 2` at the normalize boundary;
- aggregate-defect case preserves the normalize contract and deviates only afterward.

A comparison run with both injected defects disabled restored output `10`. This is a bounded causal intervention, but the fixture intentionally does not generalize this into a universal debugging algorithm.

## ENGINEERING JUDGMENT

High-value observability records should be selected to answer discriminating questions, not merely maximize volume. For async/distributed work, useful records commonly need stable operation/request identity, semantic stage/state, outcome/failure classification, relevant version/artifact/environment identity, and timing/order information where the claim depends on ordering. Sensitive values must not be logged merely because they aid debugging.

Instrumentation can also perturb timing, allocation, I/O, scheduling and failure behavior. Therefore `instrumented reproduction` and `unmodified production behavior` are distinct evidence contexts when those effects are material.

## CONTRADICTION

Rejected shortcut: **“the stack trace/log line closest to the symptom is the root cause.”** The fixture demonstrates that identical final symptoms can originate in different prior stages. Location and correlation are evidence inputs, not causal verdicts.
