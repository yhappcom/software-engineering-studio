## Problem: a Git commit is not a run-completion oracle

A user observed no new visible Studio progress and suspected the hourly research job had stopped. A check of the existing automation exposed separate facts:

- The task remained **enabled**, with an `Asia/Seoul` hourly schedule at minute 29.
- A recent scheduled task had an actual `last_run` with terminal `completed`, and its `latest_result.run_id` matched that run's ID. The result was created after the run started, so it was not merely an older run's saved answer.
- The reported result explicitly said no new trustworthy product/independent validation had occurred, and **no new Studio commit was generated by that cycle**.
- The then-latest publicly observable Studio `main` commit was `0216130d81a9f59bef6b26d853648c22a3493aff`, recorded earlier than the later completed automation. Thus `no later commit` did **not** imply `no later execution`.
- The platform reported notification delivery as **unknown** and supplied **no confirmed future-run timestamp** even though the task was enabled with a recurring schedule. Neither field proves the app showed an update or that the scheduler had paused.

These are observations of one accessible latest run and the GitHub repository, **not exhaustive proof that every intervening hourly trigger fired on time**. Private task IDs, chat references and any account-specific transcript are intentionally omitted from this public reusable study.

## Root cause discipline

**Observed symptom:** lack of a new public research commit and lack of a visible result.

**Falsified hypothesis:** the absence of a newer Git commit necessarily means the task did not execute. There is a recorded successful run after that commit.

**Not established:** whether the platform sent a notification, whether the user saw a particular UI, any systemic delivery failure, or the complete run history between observed checkpoints. A single completed run cannot establish uninterrupted hourly liveness. Run timing variations are not by themselves failure.

**Quality issue independent of scheduling:** the completed run reiterated already-known OPEN states and produced no new executable evidence or independent source finding. That is a substantive-work selection weakness, not a scheduler execution failure. The Balance Loop should pivot from unchanged product state to a genuine independent prerequisite, without manufacturing filler commits.

## Five independent gates

| Gate | Required evidence | False-positive to reject |
| --- | --- | --- |
| **A. Scheduling configured** | Enabled and a concrete time-zone-aware schedule | Enabled implies a trigger already executed |
| **B. Actual execution** | Run ID, `scheduled_for`, `started_at`, terminal `recorded_status` | Repository commit count or stale `last_run_time` |
| **C. Result binding** | Same run ID in latest result, result timestamp not older than that attempt, failure flag considered | Old successful `latest_result` copied onto a failed/retried run |
| **D. Evidence promotion** | Exact source ref, test oracle and execution observations, or verified new Studio commit linked to this run | Green CI, generated note or unchanged repo interpreted as autonomous quality improvement |
| **E. User delivery** | Independent explicit delivery acknowledgement when available | Published chat reference or `delivery_status=unknown` interpreted as notification success |

The five gates are orthogonal. An automation can pass B/C but have no material D and unknown E. An application may also show an old delivered result while B has failed for the latest run.

## Alternatives and corrective action

- **Commit-count-only monitor:** inexpensive but provably unsound. It conflates successful no-delta runs with missing execution and incentivizes low-value write noise. Reject.
- **Run-status-only monitor:** correctly distinguishes stopped/missing execution but cannot establish research value, durable publication or notification. Use as a necessary, insufficient signal.
- **Five-gate evidence chain:** preferred. Verify run status and result provenance first; compare only meaningful repository delta; independently verify delivery if the platform exposes it; report uncertainty otherwise.
- **Run-content policy improvement, applied:** the existing hourly research prompt was revised without changing its schedule or creating a duplicate task. A no-delta product ref now triggers a substantive **independent public/generic executable or authoritative-source study** rather than repeated OPEN summaries. Results must identify VERIFIED EXECUTION, NEW EVIDENCE/CONTRADICTION, DEPENDENCY/HANDOFF, or explicit NO MATERIAL DELTA; only meaningful findings are committed. Neither private LogMate sources nor user files/credentials may be copied to public Studio Actions or artifacts.
