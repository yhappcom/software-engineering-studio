# D005 — Torn durable-write recovery model

Status: **IN STUDY — bounded executable MODEL, not physical power-loss validation**  
Date: 2026-09-19  
Lead: Data, Persistence & Distributed Systems

## Problem
The prior D005 short-write fixture established that a positive short `pwrite` can be retried to completion. That must not be generalized to a torn durable write: after a crash/power loss, durable media can contain a mixture of old and new sectors even though the application previously issued a full write.

## SOURCE
Primary SQLite material checked 2026-09-19:
- `https://www.sqlite.org/atomiccommit.html` — rollback-mode atomic commit explicitly assumes sector writes need not be atomic; SQLite journals complete sectors needed for recovery and documents crash-test VFS simulation of incomplete sector writes, garbage and reordering.
- `https://www.sqlite.org/psow.html` — powersafe overwrite constrains collateral damage outside the application-written byte range; it does not require the written range to contain all-old or all-new bytes. SQLite does not assume database-page writes are atomic and documents torn-page recovery.
- `https://www.sqlite.org/testing.html` — SQLite crash tests use alternative VFS implementations to simulate buffered-filesystem crash states, including reordered/corrupted unsynchronized writes, then reopen and verify all-or-none transaction state plus integrity.
- `https://www.sqlite.org/vfs.html` — VFS is the filesystem abstraction and SQLite's test VFS/shims are used to simulate filesystem faults and verify journal/write/sync ordering.

## SYNTHESIS
`short syscall return` and `torn durable write` are different failure classes.

- short syscall return: an immediate API-level progress/result observation; the caller/VFS may retry remaining bytes;
- torn durable write: a post-crash persistence state in which only part of a larger intended write reached durable media.

A successful full write call therefore does not by itself establish an atomic durable page image.

## EXECUTABLE MODEL
Fixture: `research/data/fixtures/D005_torn_write_recovery_model.py`  
Environment: Python 3.13.5 / Linux, executed 2026-09-19.

### CLAIM
A multi-sector page can be neither the old nor the new atomic state after a modeled crash, and recovery requires independently durable information sufficient to reconstruct an accepted atomic state.

### PROPERTY / ORACLE
For a transaction-level atomic page transition, accepted post-recovery page state is exactly `old` or `new`. The fixture constructs independent byte arrays for those two states and compares the modeled post-crash/recovery bytes directly.

### INPUT / FAILURE MODEL
A 4096-byte page is divided into eight 512-byte sectors. The model applies the new bytes to the first three sectors and leaves the remaining five sectors old, representing a bounded linear torn durable page.

### OBSERVATION
Execution produced:
- old hash prefix `f1a9116e64d5ce92`;
- new hash prefix `1608902a40daa76c`;
- torn hash prefix `98e338ab5d089497`;
- torn page failed the atomic-state oracle;
- complete old pre-image restored the accepted old state;
- deliberate partial-pre-image mutant failed to reconstruct the old state.

### VERDICT
**VALIDATION — MODEL PASS.** The executable model distinguishes torn persistence from short-write progress and demonstrates why recovery evidence must include sufficient durable pre-image/recovery information rather than merely retrying an API-level remainder.

## ROOT-CAUSE CONNECTION TO SQLITE
**SOURCE:** SQLite's rollback-mode design journals complete sectors/pages needed to recover from non-atomic sector/page writes, and its own crash tests deliberately simulate incomplete/reordered/corrupted unsynchronized writes. This is consistent with the model's mechanism.

**EVIDENCE LIMIT:** the fixture does **not** execute SQLite through a custom crash VFS and does not physically interrupt a disk/device. It therefore does not prove SQLite recovery on this host, filesystem, storage device, Android/iOS stack, WAL mode, or actual power loss. SQLite's own published crash-testing methodology is SOURCE evidence, not execution evidence generated by this Studio run.

## CONTRADICTION / QUEUE CORRECTION
The prior queue phrase `short/torn write` was too coarse. The short-write study already established retryable positive syscall progress. This block preserves torn durable persistence as a separate mechanism and prevents the earlier syscall result from being misread as power-loss durability evidence.

## ALTERNATIVES
- rollback/pre-image recovery: preserve sufficient old state before overwriting durable database content;
- WAL/new-image recovery: publish committed new state through a different ordering/recovery protocol;
- storage-advertised atomic-write capabilities: can change the required protocol only when the capability is trustworthy and correctly surfaced.

These are mechanism families, not a LogMate/MintTap implementation decision.
